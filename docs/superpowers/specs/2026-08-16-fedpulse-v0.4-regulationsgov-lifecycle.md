# FedPulse v0.4 — Regulations.gov docket lifecycle enrichment

## Product thesis

FedPulse v0.3 makes Federal Register and GPO MARC monitoring production-trustworthy. v0.4 should make FedPulse more useful by turning isolated Federal Register publications into docket-centered regulatory lifecycles.

The goal is not prediction. The goal is to answer:

> Where is this regulatory action in its lifecycle, what changed since the last run, and which official docket evidence proves it?

## Why Regulations.gov next

Federal Register records are the publication layer. Regulations.gov is the participation and docket layer. Joining the two lets FedPulse show whether a signal is merely a publication burst or part of a durable action path:

1. notice / proposed rule appears in the Federal Register
2. docket opens or receives supporting material
3. comment volume changes
4. agency posts new documents, attachments, meetings, or notices
5. final rule or withdrawal appears
6. effective date, compliance date, or litigation-sensitive follow-up emerges

That gives users a stronger intelligence unit than "document" or "package": a docket lifecycle.

## Stage taxonomy

Use deterministic stages. Avoid subjective language.

| Stage | Meaning | Minimum evidence |
|---|---|---|
| `pre_rulemaking_signal` | Docket activity exists without a linked proposed/final rule yet | Regulations.gov docket + agency/topic match |
| `proposal_comment_window` | Proposed rule or notice has a comment period | FR proposed rule/notice + docket/comment metadata |
| `comment_window_closed` | Comment period ended and no final rule is linked yet | comment close date < as_of |
| `agency_review_activity` | New supporting materials, attachments, or agency documents posted after close | docket document deltas after close |
| `final_rule_published` | Final rule linked to same docket/topic | FR final rule + docket/document match |
| `withdrawn_or_terminated` | Withdrawal, termination, or no-action disposition appears | FR/doc title/action exact phrases |
| `implementation_followup` | Effective/compliance/amendment/correction follow-up appears | FR rule/correction + linked docket/package |

## Linking strategy

### Strong links

A link is high confidence when any of these are true:

- FR `docket_ids` exactly matches Regulations.gov `docketId`
- FR document URL or metadata references a Regulations.gov docket ID
- Regulations.gov document metadata references a Federal Register document number

### Medium links

A link is medium confidence when all are true:

- canonical agency matches
- normalized title/topic token overlap clears threshold
- dates are within a bounded window
- no competing docket for the same agency/topic scores higher

### Rejected links

Reject links based only on same agency + same week. That repeats the v0.1 package flaw and will create noisy lifecycle claims.

## Data ingestion

Add `src/fedpulse/regulations_client.py` using stdlib `urllib` only.

Functions:

```python
search_dockets(agency: str | None, updated_since: str | None) -> list[dict]
fetch_docket(docket_id: str) -> dict
fetch_docket_documents(docket_id: str) -> list[dict]
to_docket_record(raw: dict) -> dict
to_docket_document_record(raw: dict) -> dict
```

Add tables:

```sql
CREATE TABLE IF NOT EXISTS dockets (
  docket_id TEXT PRIMARY KEY,
  source TEXT NOT NULL DEFAULT 'regulations.gov',
  agency_id TEXT,
  agency_name TEXT,
  title TEXT,
  docket_type TEXT,
  status TEXT,
  opened_at TEXT,
  last_activity_at TEXT,
  comment_close_date TEXT,
  comment_count INTEGER,
  document_count INTEGER,
  attachment_count INTEGER,
  official_url TEXT,
  raw_json TEXT,
  created_at TEXT DEFAULT (datetime('now')),
  updated_at TEXT DEFAULT (datetime('now'))
);

CREATE TABLE IF NOT EXISTS docket_documents (
  document_id TEXT PRIMARY KEY,
  docket_id TEXT NOT NULL,
  agency_id TEXT,
  title TEXT,
  document_type TEXT,
  posted_at TEXT,
  fr_document_number TEXT,
  official_url TEXT,
  raw_json TEXT,
  created_at TEXT DEFAULT (datetime('now')),
  updated_at TEXT DEFAULT (datetime('now')),
  FOREIGN KEY (docket_id) REFERENCES dockets(docket_id) ON DELETE CASCADE
);

CREATE TABLE IF NOT EXISTS record_docket_links (
  record_id TEXT NOT NULL,
  docket_id TEXT NOT NULL,
  confidence TEXT NOT NULL,
  method TEXT NOT NULL,
  evidence_json TEXT NOT NULL,
  created_at TEXT DEFAULT (datetime('now')),
  PRIMARY KEY (record_id, docket_id),
  FOREIGN KEY (record_id) REFERENCES records(id) ON DELETE CASCADE,
  FOREIGN KEY (docket_id) REFERENCES dockets(docket_id) ON DELETE CASCADE
);
```

## Pipeline integration

Add optional `--skip-regulations` flag to `fedpulse.pipeline_v2`.

Pipeline order:

1. ingest Federal Register
2. sync MARC
3. sync Regulations.gov dockets/documents
4. normalize agencies
5. detect packages
6. link FR records/packages to dockets
7. compute lifecycle output
8. apply lifecycle state
9. publish atomic snapshot

Regulations.gov failure should degrade `health.json`, not fail the whole run, unless a malformed response would corrupt persisted docket state.

## Acceptance criteria

v0.4 is complete when:

1. `lifecycle.json` is published atomically with the existing outputs.
2. The dashboard shows docket lifecycle cards without breaking v0.3 signal cards.
3. Federal Register records with exact docket IDs link to docket lifecycle items.
4. Same-agency-only links are rejected.
5. Lifecycle stage transitions are persisted and notify only on meaningful transitions.
6. Regulations.gov outage or rate-limit state appears in `health.json` without corrupting existing FR/MARC output.
7. CI covers ingestion, linking, stages, output contract, and dashboard rendering assumptions.

## Do not build in v0.4

- LLM summaries
- embeddings
- comment text analysis
- full-text classification
- user accounts
- paid notification workflow
- additional sources beyond Regulations.gov

Keep v0.4 focused: docket lifecycle enrichment, deterministic evidence, production-safe output.
